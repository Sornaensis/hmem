# Embeddings and similarity search

Embeddings are optional. hmem works without them. pgvector stores and compares
vectors; it does not generate them. You can supply vectors yourself or opt into
automatic GPU vectorization.

## Enable pgvector

Run these commands with the configuration for the database you want to use:

```bash
hmem-ctl pgvector status
```

For Compose, use `docker compose run --rm hmem hmem-ctl pgvector status`.
The default `postgres:17-bookworm` image does not include pgvector. Native
installations need a pgvector package matching the configured PostgreSQL server;
install it on that server, rather than on the hmem client machine.

Follow the reported `next action`. Once the package is available and migrations
are applied, enable the database objects:

```bash
hmem-ctl pgvector enable
```

In production, take a backup and schedule a change window: creating the column
and index can block writes. Enablement does not install packages, apply ordinary
migrations, or replace incompatible existing objects.

| Status | Action |
| --- | --- |
| `ready` | Storage and cosine search are available. No vectors are generated by enablement. |
| `package_missing` | Install a matching pgvector package/image, then enable. |
| `observations_table_missing` | Run `hmem-ctl migrate` against this database first. |
| Missing extension, column, or index | Run `hmem-ctl pgvector enable`. |
| Unusable, invalid, or incompatible object | Have a database administrator repair the reported object, then check again. |

`status` exits with 0 when ready, 2 when inspected but not ready, and 1 for an
operational error. Do not recreate a data volume to add pgvector.

## Choose how to generate vectors

- **Manual:** use an external producer and the file workflow below, or write
  individual vectors through [REST or MCP](api.md). hmem does not call a provider
  during export/import.
- **Automatic:** use the opt-in [Docker GPU setup](docker.md). It needs pgvector
  and a validated GPU provider. Automatic vectorization is disabled by default
  and has no CPU fallback. Provider failure leaves ordinary hmem operations
  available, but prevents new automatic vectors.

Each Observation stores one vector. An enabled automatic provider can replace
manual vectors from a different space, so coordinate manual imports with its
configured target.

## Manual export, generate, import

1. Export work for one workspace, replacing the UUID and space label:

   ```bash
   hmem-ctl embeddings export --workspace <workspace-uuid> \
     --space-fingerprint <your-space-label> --output embedding-input.ndjson
   ```

   Choose a stable, nonblank space label without whitespace that identifies your
   model revision and input formatting. Export selects missing vectors and those
   in another space. Add `--all` when regenerating the complete workspace, such as
   after changing models. Omitting the space selects `hmem:legacy-manual:v1`.
2. Have your external producer read each exported Observation and write one JSON
   result per line to `embedding-results.ndjson`. Each result must contain
   **only** these fields:

   | Field | Value |
   | --- | --- |
   | `format_version` | Preserve the exported value (`2`). |
   | `observation_id`, `workspace_id` | Preserve the exported IDs. |
   | `content_fingerprint`, `space_fingerprint` | Preserve both exported values. |
   | `embedding` | Exactly 1536 finite numbers generated from the exported input. |

   Do not copy the export-only `git_sha`, `subjects`, or `content` fields into
   result records, or recalculate the fingerprint. Duplicate Observation IDs,
   lines over 1 MiB, and inputs over 100000 records are rejected.
3. Import the results:

   ```bash
   hmem-ctl embeddings import --input embedding-results.ndjson --json
   ```

   `--json` prints per-record outcomes and a summary. Use `--output`/`--input`
   files on Windows to avoid shell redirection changing the file encoding.
   Without these options, export writes stdout and import reads stdin.

Import accepts valid records independently: a failed line does not undo successful
lines. Exit 0 means everything applied or was already satisfied; exit 2 means
some records failed; exit 1 means setup, file access, or database/capability failure.

| Outcome | What to do |
| --- | --- |
| `applied`, `already_satisfied` | Nothing; retrying the same result is safe. |
| `stale` | Re-export current input, regenerate, and retry. |
| `not_found` | Check that the Observation/workspace pair still exists. |
| `rejected` | Correct the reported format, vector, duplicate, or size problem. |
| `database_error` | Fix the database problem, then retry the failed record. |

Older version-1 imports remain supported without `space_fingerprint` and belong
to the legacy manual space. New exports always use version 2.

## Compatibility and queries

Use the same model revision, input formatting, and vector space for stored and
query vectors. A space label is a compatibility claim; relabeling an old vector
does not convert it. When changing models, export with `--all` and regenerate
the corpus in the new space before querying it.

Generate query vectors externally, then call REST
`POST /api/v1/observations/similar` or MCP `observation_similar`. There is no
raw-text query embedding endpoint. Supply the matching `space_fingerprint`;
omitting it searches only the legacy manual space. Explicit null is invalid.
See [the API guide](api.md) for authentication and OpenAPI request details.

Content writes, including same-text re-audits, clear an Observation's stored
vector. It stays out of similarity results until a new vector is stored. A
changed-content import is stale and needs fresh export input; unchanged input
can still be reused after a same-text re-audit.
